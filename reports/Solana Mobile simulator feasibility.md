# Build the missing layer, not another CLI

The Solana Mobile Simulator is technically feasible, but most of its original v0.1 plan has already been built by Solana Mobile itself. Since May 2026 the company has shipped an official, Apache-2.0 command-line tool, `solana-mobile` on npm (stable 0.6.0 released 2026-10-09, with new canary builds almost every day). It already has `doctor`, `create`, emulator management, device install of a test wallet, a localnet with automatic port forwarding, and an MWA "playground" that streams wallet results to the terminal ([solana-mobile-cli README](https://github.com/solana-mobile/solana-mobile-cli), [CLI overview](https://docs.solanamobile.com/cli/overview)). This matters because the platform itself is simple to imitate: Seeker is a normal Android phone (Android 16 since the MR7 update) with a thin layer of Solana parts on top. Solana Mobile says any Android device or emulator is enough for nearly all development ([Seeker docs](https://docs.solanamobile.com/solana-mobile-stack/seeker.md), [MR7 notes](https://docs.solanamobile.com/seeker/release-notes/mr7.md)). The hard limits are clear and permanent. Nobody can emulate the secure hardware (TEE, secure element, device attestation), and nobody can obtain a real Seeker Genesis Token or .skr domain on an emulator. What is still missing, and what the project can really add, is narrower: a test wallet that approves or rejects requests automatically for CI, tracing of MWA sessions inside the developer's own app, easy setup of the Seed Vault simulator, Seeker look-alike test identities on devnet or localnet, and good support for non-Expo frameworks. The recommended path is to stop planning a parallel Rust CLI that repeats `doctor`/`dev`/`install`, and to build a small companion toolkit that uses the official CLI for the basics. Features that belong upstream should go upstream.

## Seeker is ordinary Android with a thin crypto layer on top

The most important technical fact for a simulator is that Solana Mobile did not build a new operating system. Seeker started on Android 15 and moved to **Android 16 in the MR7 update (builds dated March 2026)**. The latest release notes found, MR8, are dated June 2026 by their build strings ([MR7](https://docs.solanamobile.com/seeker/release-notes/mr7.md), [MR8](https://docs.solanamobile.com/seeker/release-notes/mr8.md)). The older Saga phone stopped at Android 14 and **reached end of support on 2025-10-21** ([Solana Mobile Support](https://support.solanamobile.com/en/articles/12600995-saga-end-of-support)). On top of Android, Solana Mobile adds four things. These are the Seed Vault system service, the built-in Seed Vault Wallet, the built-in dApp Store, and on-chain device identity assets. The OTA system updates ship fixes to Seed Vault and new versions of the built-in store and wallet. This shows that these parts belong to the system image, not to normal user-installed apps ([MR7](https://docs.solanamobile.com/seeker/release-notes/mr7.md), [MR6](https://docs.solanamobile.com/seeker/release-notes/mr6.md)). The phone reports itself to apps as `Model: "Seeker"`, `Brand: "solanamobile"`, `Manufacturer: "Solana Mobile Inc."`. Solana Mobile's own docs say this check "can be spoofed" ([Detecting Seeker Users](https://docs.solanamobile.com/recipes/general/detecting-seeker-users)). So a stock Android emulator at API 35 or 36, with those build properties changed, matches Seeker's software baseline well.

**Seed Vault** is where the secure hardware lives. It is "a system service providing secure key custody to Wallet apps". Seeds stay inside the secure execution environment, backed by the Android Keystore, and every signature needs fingerprint or PIN approval through system UI ([Seed Vault docs](https://docs.solanamobile.com/solana-mobile-stack/seed-vault.md)). Wallets talk to it through a public Wallet API made of intents (`ACTION_AUTHORIZE_SEED_ACCESS`, `ACTION_SIGN_TRANSACTION`, `ACTION_GET_PUBLIC_KEY`) and a content provider with tables such as `authorizedseeds`, `accounts` and `implementationlimits`. Keys follow BIP-39, BIP-32 and SLIP-0010, and the usual paths `m'/44'/501'/X'` are pre-derived ([integration guide](https://github.com/solana-mobile/seed-vault-sdk/blob/main/docs/integration_guide.md)). Solana Mobile also publishes an **official Seed Vault simulator** that runs as an ordinary app on any Android API 31+ device. It comes with a warning that it "makes zero guarantees about security" ([seed-vault-sdk](https://github.com/solana-mobile/seed-vault-sdk)). One detail matters here: the SDK is aimed at *wallet* developers. The docs tell dApp developers to "use the MWA SDK instead" and never to touch Seed Vault directly ([Seed Vault docs](https://docs.solanamobile.com/solana-mobile-stack/seed-vault.md)). The SDK is maintained but not moving fast. Its last tagged release is v0.4.0 from 2025-10-06, and recent commits are mostly Dependabot bumps ([releases](https://github.com/solana-mobile/seed-vault-sdk/releases), [commits](https://github.com/solana-mobile/seed-vault-sdk/commits/main)).

The **dApp Store** is a preinstalled Android store for native APKs and wrapped web apps. Publishing happens on-chain (an App NFT) through the Publisher Portal or the `dapp-store` CLI, using a Solana keypair and a portal API key. The store accepts only release-signed builds ([Publishing CLI](https://docs.solanamobile.com/dapp-store/publishing-cli.md), [dApp Store intro](https://docs.solanamobile.com/dapp-store/intro.md)). The old `init`/`validate`/`publish` commands were removed. Pre-submission checks now live in `solana-mobile release check` ([dapp-publishing](https://github.com/solana-mobile/dapp-publishing)). No official way to install the store app itself on an emulator was found, and its license is unknown. So a simulator should not ship that APK.

**Seeker-only features** are mostly on-chain mainnet assets that are minted once per device. The **Seeker Genesis Token (SGT)** is a Token-2022 NFT in group `GT22s89nU4iWFkNXj1Bw6uYhJJWDRPpShHt4Bk8f99Te`, minted into the Seed Vault Wallet, and checked with the `@solana-mobile/skr-genesis-token` package against mainnet RPC ([SGT docs](https://docs.solanamobile.com/solana-mobile-stack/seeker-genesis-token.md)). Every owner also gets a **.skr domain** (built on AllDomains, read with `@solana-mobile/skr-domain`) ([.skr docs](https://docs.solanamobile.com/solana-mobile-stack/skr-domain.md)). **SKR** is a mainnet SPL token with a staking program ([SKR docs](https://docs.solanamobile.com/solana-mobile-stack/skr.md)). **TEEPIN** is described only as a three-layer design: hardware TEE attestation, on-chain verification, and a Guardian network. No public developer API was found for it ([Solana Mobile blog](https://solanamobile.com/blog/solana-mobile-the-web3-mobile-evolution)). The recommended anti-sybil check is Sign In With Solana plus SGT ownership ([Detecting Seeker Users](https://docs.solanamobile.com/recipes/general/detecting-seeker-users)). Any device can *read* these assets, because they are plain RPC calls. Only a real Seeker can *mint* them.

The ecosystem is also growing past two phones. Solana Mobile claims **over 200,000 Seekers sold**. In March 2026 it opened the stack to any Android maker, and on 2026-10-15 it named Ledger's Atom phone (shipping summer 2027, with a secure element) as the first partner. Atom will preinstall a "Seeker app" that merges the store and the wallet ([PR Newswire](https://www.prnewswire.com/news-releases/solana-mobile-announces-ledger-as-its-first-hardware-expansion-partner-302909677.html)). This makes a simulator that does not depend on one hardware model more useful, but it also means the real Seed Vault backends will become more varied (Trustonic TEE, Ledger secure element). No simulator can copy them.

## Mobile Wallet Adapter runs fine on any emulator

The Mobile Wallet Adapter (MWA) is the protocol that dApps actually use, and it is fully software. The current spec is **2.0, with a 2.1.0 changelog entry** that adds an optional wallet icon ([MWA spec](https://solana-mobile.github.io/mobile-wallet-adapter/spec/spec.html)). In "local association", the dApp opens a `solana-wallet:/v1/associate/local?association=<key>&port=<port>&v=<version>` intent. The wallet then starts a WebSocket server on localhost, and the two sides agree on a key using P-256 ECDH and HKDF. After that, every JSON-RPC message is encrypted with AES-128-GCM and carries a sequence number ([MWA spec](https://solana-mobile.github.io/mobile-wallet-adapter/spec/spec.html)). The methods are `authorize` (which also handles silent re-authorization and the optional Sign In With Solana payload), `deauthorize`, `get_capabilities`, `sign_messages` and `sign_and_send_transactions`. The older `reauthorize` and `sign_transactions` are deprecated. The spec defines clear error codes, from `-1` (authorization failed) to `-7` (chain not supported), plus `-100` for web-origin attestation ([MWA spec](https://solana-mobile.github.io/mobile-wallet-adapter/spec/spec.html)). Those codes map directly onto "failure scenarios" that a test tool could offer. The spec also has timing rules: the wallet listens for at least 10 seconds, the dApp waits at least 30 seconds, and the HELLO handshake must finish within 10 seconds. A slow, cold-booting emulator can break these limits ([MWA spec](https://solana-mobile.github.io/mobile-wallet-adapter/spec/spec.html)).

There are two official test wallets, and each has a weak spot. **fakewallet** lives in the MWA monorepo and has prebuilt APKs on GitHub releases (both "v1" and "legacy" protocol builds). It makes real Ed25519 signatures from a BIP-39 seed and can send transactions to devnet, testnet, mainnet or `http://localhost:8899` ([releases](https://github.com/solana-mobile/mobile-wallet-adapter/releases), [ViewModel source](https://github.com/solana-mobile/mobile-wallet-adapter/blob/main/android/fakewallet/src/main/java/com/solana/mobilewalletadapter/fakewallet/MobileWalletAdapterViewModel.kt)). It has buttons such as "Simulate auth token invalid", "Simulate too many payloads" and "Simulate submit failed" ([strings.xml](https://github.com/solana-mobile/mobile-wallet-adapter/blob/main/android/fakewallet/src/main/res/values/strings.xml)). However, a human must tap them. No intent extra or ADB hook for scripting them was found. **Mock MWA Wallet** is the wallet the docs now *recommend*. It imitates the Seed Vault Wallet's bottom-sheet approval and can import a fixed private key through `local.properties`. But it has **no published APKs**, so you must build it in Android Studio. It needs a **secure lock screen**, and you must tap "Authenticate" to unlock signing for 15 minutes ([mock-mwa-wallet](https://github.com/solana-mobile/mock-mwa-wallet), [test with any Android device](https://docs.solanamobile.com/recipes/general/test-with-any-android-device)). The two official docs pages describe the mock wallet differently. One says it keeps no persistent keypair, while the repo documents key import. So part of the docs is probably out of date.

Web dApps have one more limit. On Android, MWA works only in **Chrome** (including Chrome PWAs). It does not work in Firefox, Brave or Opera, and it does not work on iOS at all ([web apps docs](https://docs.solanamobile.com/get-started/web/apps)). Desktop browsers can connect only through remote association: a QR code plus a "reflector" WebSocket server that the app must supply ([web installation](https://docs.solanamobile.com/mobile-wallet-adapter/web-installation)). No official public reflector host was found. For a simulator, the practical meaning is simple: drive Chrome on the emulator, and treat remote association as "bring your own reflector".

The pain points that developers report are almost all about *seeing why a session failed*. On Stack Exchange there are unanswered posts about a `CancellationException` when signing in with Mock MWA Wallet ([SE 23878](https://solana.stackexchange.com/questions/23878/how-to-fix-mock-mwa-wallet-error-when-signing-in)) and a transaction "stuck on loading" ([SE 22907](https://solana.stackexchange.com/questions/22907/transaction-stuck-on-loading-with-mock-mwa-wallet-is-there-something-wrong-in)). MWA issue #862, open since June 2024, asks for developer features in fakewallet because Phantom and Solflare "lag or crash on emulators". The maintainers reduced its scope to APK distribution and key injection, and they ruled a transaction inspector **out of scope** ([issue #862](https://github.com/solana-mobile/mobile-wallet-adapter/issues/862)). That refusal is a useful signal: a protocol-level inspector is something the official team has chosen not to build.

## The official `solana-mobile` CLI already covers most of the `sms` plan

The original plan in About.txt listed "audit existing official Solana Mobile SDKs, mock wallets, and Seed Vault simulation capabilities" as its first priority. That audit changes the project. The npm package `solana-mobile` was **first published 2026-05-22**. It is developed in `solana-mobile/solana-mobile-cli` under Apache-2.0, and in October 2026 it was releasing canaries almost daily ([npm registry](https://registry.npmjs.org/solana-mobile), [README](https://github.com/solana-mobile/solana-mobile-cli)). Its `doctor` checks JS tooling, the JDK, the Android SDK, emulators and devices, prints readiness per workflow, offers `--json`, and exits with code 1 when something is missing. Its `emulator` commands create, start, stop, list and tune AVDs and install system images without Android Studio. `device install fakewallet` downloads a cached, sha256-checked APK, and `device tune` turns off animations, autofill, Chrome first-run prompts and the lock screen "for automation". `localnet` runs Surfpool or solana-test-validator in Docker and forwards ports 8899, 8900 and 18488 to every device with `adb reverse`, re-applying them after a reboot. `playground` serves an MWA test page that covers connect, Sign In With Solana, sign message, sign transaction and sign-and-send, and it streams every result to the terminal ([README](https://raw.githubusercontent.com/solana-mobile/solana-mobile-cli/main/README.md), [CLI device](https://docs.solanamobile.com/cli/device), [CLI emulator](https://docs.solanamobile.com/cli/emulator), [CLI playground](https://docs.solanamobile.com/cli/playground)). Scaffolding also moved there (`npx solana-mobile@latest create`, with templates in `solana-mobile/templates`), and older scaffolds are archived or stale ([templates](https://github.com/solana-mobile/templates), [org repos](https://github.com/orgs/solana-mobile/repositories)).

The table below compares the proposed commands from About.txt with what already exists.

| Proposed `sms` command | Official equivalent today | Overlap |
|---|---|---|
| `sms doctor` | `solana-mobile doctor [--json]` | Full |
| `sms init` | `solana-mobile create` (templates) | Full for Expo, partial otherwise |
| `sms dev` | `emulator start` + `device install fakewallet` + `localnet start` | High (several commands, not one) |
| `sms devices` | `device list [--json]`, `emulator list/status` | Full |
| `sms install <apk>` | `device install <apk> [--grant] [--all]` | Full |
| `sms logs` | `localnet logs`, playground stream | Partial (no app or wallet logcat, no MWA trace) |
| `sms tx <sig>` | Playground results, Surfpool Studio | Partial |
| `sms stop` | `emulator stop`, `localnet stop` | Full |

The official tool still leaves some real gaps. Its catalog lists only `fakewallet`. It has **no Seed Vault simulator and no Mock MWA Wallet entry**, and the CLI pages do not mention Seeker identity spoofing ([README](https://raw.githubusercontent.com/solana-mobile/solana-mobile-cli/main/README.md), [CLI device](https://docs.solanamobile.com/cli/device.md)). Its `release build/check` flow targets Expo apps specifically. It needs Node, plus Docker for localnet. The playground shows only *its own* test page, not the MWA sessions of the developer's app. A search of GitHub found **no community "Solana Mobile simulator" or MWA CI harness** at all. The community MWA projects that exist are bindings with 0 to 2 stars ([GitHub search](https://github.com/search?q=solana+mobile+simulator&type=repositories)). Two facts should be read with care. The official CLI has only 4 GitHub stars, and npm download counts were not collected, so how many people use it is unknown. The contents of the 0.7.0 canaries were also not checked, so some gaps listed here may already be closing.

There is one technical conflict to keep in mind. `device tune` *disables* the lock screen, while Mock MWA Wallet *requires* a secure one ([README](https://raw.githubusercontent.com/solana-mobile/solana-mobile-cli/main/README.md), [docs recipe](https://docs.solanamobile.com/recipes/general/test-with-any-android-device.md)). Any tool that adds Mock MWA Wallet to an automated setup must handle this, for example by setting a PIN and then using emulator fingerprint touches.

## The building blocks work on macOS, but CI and hardware set hard limits

Building the orchestration itself is routine engineering. The classic Android tools (`sdkmanager`, `avdmanager`, `emulator`, `adb`) are documented, scriptable and well understood. Headless flags (`-no-window -gpu swiftshader_indirect -no-snapshot -noaudio -no-boot-anim`), console and adb port pairs (5554 to 5682), and named snapshots (`-snapshot <name>`, `-no-snapshot-save`) are all documented ([emulator command line](https://developer.android.com/studio/run/emulator-commandline), [android-emulator-runner](https://github.com/ReactiveCircus/android-emulator-runner)). Two changes from 2026 matter. Google now marks **`sdkmanager` and `avdmanager` as deprecated** in favor of a new `android` CLI (`android emulator create|start|stop`, `android sdk install`) ([sdkmanager](https://developer.android.com/tools/sdkmanager), [Android CLI commands](https://developer.android.com/tools/agents/android-cli/commands)). Apple Silicon also needs `arm64-v8a` system images, and Play Store images block `adb root` ([arda.pw guide](https://arda.pw/posts/android-emulator-macos-without-android-studio/)). Inside the emulator, `10.0.2.2` is the host's loopback address, and `adb reverse` lets the app use `localhost:8899` on both emulators and USB phones ([emulator networking](https://developer.android.com/studio/run/emulator-networking-address)). For the network, Surfpool is the documented drop-in replacement for `solana-test-validator`. It can fork mainnet or devnet just in time and can pre-fund wallets with `--airdrop` ([Surfpool CLI](https://solana.com/docs/tools/surfpool/toolchain/cli)). That matters because public devnet allows **100 requests per 10 seconds per IP**, and the web faucet allows **2 requests every 8 hours** ([Clusters](https://solana.com/docs/references/clusters), [Faucet](https://faucet.solana.com)). So a local or forked validator should be the default, not devnet.

The Rust side is also ready. `adb_client` is a maintained pure-Rust ADB library (v3.2.3, August 2026, about 134,000 downloads), and Anza's `solana-rpc-client` is at 4.3.2 ([crates.io adb_client](https://crates.io/api/v1/crates/adb_client), [crates.io solana-rpc-client](https://crates.io/api/v1/crates/solana-rpc-client)). The safest first version would still call the real `adb` binary, and it would use plain JSON-RPC over `reqwest` for `getTransaction` to keep build times low. But this is exactly the layer the official CLI already does in TypeScript. A static Rust binary with no Node dependency is a small advantage, not a reason to rebuild it.

The hard blockers fall into two groups. The first group can never be solved: TEE- and secure-element-backed key custody, hardware Keystore and key attestation, TEEPIN device attestation, trusted display paths such as Ledger Atom's "Secure Mode", and genuine SGT or .skr minting. These depend on hardware or on mainnet anti-sybil rules ([Seed Vault docs](https://docs.solanamobile.com/solana-mobile-stack/seed-vault.md), [PR Newswire](https://www.prnewswire.com/news-releases/solana-mobile-announces-ledger-as-its-first-hardware-expansion-partner-302909677.html)). The second group can be worked around but costs effort. **GitHub's arm64 macOS runners cannot run hardware-accelerated emulators**, because Apple's Virtualization Framework does not support nested virtualization ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). CI must therefore use Linux runners with KVM and x86_64 images, which are also "2-3 times faster" and cheaper ([android-emulator-runner](https://github.com/ReactiveCircus/android-emulator-runner)). This means "macOS first" for local development and Linux for CI will use **different CPU architectures** from the start, so the image ABI must be a setting. Also, the `skr-genesis-token` package hard-codes the mainnet group address. Look-alike SGTs on devnet or localnet only help if developers can inject a different group address into their verification code ([SGT docs](https://docs.solanamobile.com/solana-mobile-stack/seeker-genesis-token.md)). Some practical details are not yet confirmed: whether the Seed Vault simulator needs a privileged or system install on an emulator (its permission has a "privileged protection level" check), whether the fakewallet APKs run on both arm64 and x86_64, and whether Android 14 to 16 limits on background activity starts affect scripted MWA launches.

## Feasibility: a narrow companion toolkit is worth building

### What the simulator would genuinely add

After removing everything the official CLI already does, five gaps remain, and each has evidence behind it. First, **a headless, policy-driven test wallet for CI**. Today both official wallets need human taps, biometrics or a 15-minute "Authenticate" window. Nobody, official or community, has published a wallet that approves or rejects requests from a scenario file (for example "approve authorize, return -3 on the second sign") ([mock-mwa-wallet](https://github.com/solana-mobile/mock-mwa-wallet), [fakewallet strings](https://github.com/solana-mobile/mobile-wallet-adapter/blob/main/android/fakewallet/src/main/res/values/strings.xml)). This is the single strongest reason for the project to exist. Second, **MWA session tracing for the developer's own app**: one view that combines dApp and wallet logcat, association and handshake steps, auth-token state, the decoded transaction, and the final on-chain result. The official playground does not cover this, and the MWA maintainers declined it upstream ([issue #862](https://github.com/solana-mobile/mobile-wallet-adapter/issues/862)). Third, **Seed Vault simulator provisioning** for wallet developers: build or fetch the simulator, install it, and load a test mnemonic without manual UI steps. No prebuilt simulator APK is distributed today ([seed-vault-sdk README](https://raw.githubusercontent.com/solana-mobile/seed-vault-sdk/main/README.md)). Fourth, a **"Seeker profile"**: an API 36 emulator with Seeker build properties, plus look-alike SGT and .skr assets on localnet, so that identity-gated code paths can be tested. Fifth, **guides and recipes for Kotlin, Flutter and Unity**, since the official release flow is Expo-centric.

### Recommended revised v0.1 scope

The original success criterion in About.txt ("launch an Android emulator, connect a mock wallet, and test a supported Solana transaction without a physical Solana Mobile phone") **can already be met today with the official CLI**, using `emulator start`, `device install fakewallet`, `localnet start` and `playground`. A v0.1 that only reaches this point would repeat existing work. A better v0.1 has a new success criterion: *a GitHub Actions job on a Linux runner boots an emulator, installs the developer's own app and a scripted test wallet, runs one MWA flow that approves and one that rejects, and fails the build if the result is wrong, with no human taps.* To reach it, v0.1 needs the following. It needs a scriptable test wallet, ideally a fork or extension of fakewallet (it already has real signing, localnet support and all the error paths), with an ADB broadcast or a config file that chooses each response. It needs a small orchestrator that calls `solana-mobile` for emulator, device and localnet work instead of reimplementing those parts. It needs a GitHub Actions template using KVM, x86_64 and cached snapshots. And it needs one example app with Maestro flows. MWA tracing (`sms logs`, `sms tx`) is a natural v0.2. Seed Vault provisioning and the Seeker profile come after that, because they serve smaller audiences (wallet developers and identity-gated apps).

### Positioning: companion and contributor, not a parallel tool

Building a parallel Rust CLI that copies `doctor`, `dev`, `devices`, `install` and `stop` is the weakest choice. The official tool moves fast, and anything it lacks today it might ship next month. There are three options. **Contribute upstream** to fit the official roadmap: add a catalog entry for the Seed Vault simulator or a scripted wallet, fix the lock-screen conflict, or add a log command. **Build a companion** (Rust is fine) that owns only the new features (scripted wallet, tracing, CI harness, Seeker profile) and calls `solana-mobile` for everything else. **Build a full replacement** in Rust. The recommendation is the first two together. Contribute small, general fixes upstream, and keep the wallet-automation and tracing features in a clearly independent community repo, because the maintainers have already said the inspector is out of their scope. Talking early with the Solana Mobile team (through the MWA and CLI repos) is cheap and reduces the risk of overlap. The name also needs thought. "Solana Mobile Simulator" and the `sms` command both suggest an official product and collide with the official "SMS" (Solana Mobile Stack) acronym. That goes against the project's own non-goal of "implying official endorsement".

### Integration boundaries

The clean boundaries follow the platform's own layers. **Delegate** to the official CLI for SDK detection, AVDs, system images, device tuning, APK install and localnet with port forwarding, and to Surfpool for the validator. **Reuse** upstream Android code without changes where possible: fakewallet as the base for the scripted wallet, the Seed Vault simulator for the wallet-developer path, and the MWA spec's error codes as the scenario vocabulary. **Own** the scenario format, the scripted-wallet control channel, log and trace correlation, and the CI templates. **Mock clearly, and never imitate secretly**: Seeker build properties and look-alike SGT and .skr assets live only on localnet or devnet, under addresses that are clearly fake, and they can be switched on only by configuration. **Exclude and document** TEE and secure-element behavior, attestation, trusted display, OTA updates, the dApp Store client APK, and real SGT or .skr minting. Mainnet should require an explicit flag and a warning, in line with the security principles in About.txt.

### Risks

The biggest risk is **upstream absorption**. Daily canaries mean the official CLI could add a scripted wallet or a log stream at any time. Contributing upstream and keeping the companion small reduces this cost. The second risk is **protocol and SDK churn**. MWA protocol 3.0 and `wallet-adapter-mobile` 3.0 shipped in October 2026, and their breaking changes were not reviewed. Many tutorials still describe 2.x ([releases](https://github.com/solana-mobile/mobile-wallet-adapter/releases)). Version-pinned compatibility tests are needed from the start. The third risk is **emulator flakiness against MWA timeouts**. Cold boots can break the 10-second and 30-second limits, and an old bug showed that a second association started too quickly fails silently ([issue #94](https://github.com/solana-mobile/mobile-wallet-adapter/issues/94)). Snapshots and retries help. The fourth risk is the **macOS-versus-Linux ABI split**, which doubles the test matrix. The fifth is **false confidence**. A green CI run on an emulator says nothing about how real Seed Vault Wallet behaves. Upstream has fixed real Seeker-only bugs, such as Seed Vault Wallet instability after repeated MWA handoffs ([issue #1578](https://github.com/solana-mobile/mobile-wallet-adapter/issues/1578)) and the stock wallet closing its bottom sheet from Chrome or TWA ([issue #1458](https://github.com/solana-mobile/mobile-wallet-adapter/issues/1458)). The tool should say plainly that final checks still need a real device. The last risk is **maintenance with a small audience**. Demand for Solana Mobile developer tools exists, but the official CLI's 4 stars and the near-empty community search suggest the developer community is small. A narrow scope that one or two people can maintain is safer than the six-phase roadmap with a desktop GUI.

## Conclusion

The research changes the question the project should ask. It is no longer "can we simulate a Solana Mobile phone?" The answer to that has been "yes, use any Android emulator" for a long time, and since 2026 the official CLI makes the setup almost one command. The useful question now is "what can developers still not *automate* or *see*?" The answer is wallet approval in CI and the inside of MWA sessions in their own apps. Those two features are small enough for a community project, they were explicitly left out by the official team, and no one else has built them.

Seen this way, the Rust choice, the `sms` name and the full command list from About.txt are less important than they first looked. What matters is a scriptable wallet that speaks real MWA, a trace view built on the spec's own error codes, and a CI recipe that runs on Linux. If the project begins by forking fakewallet and talking with the upstream maintainers, it can show working CI tests within its first release. It can also become something the official tool links to, rather than something it replaces.
